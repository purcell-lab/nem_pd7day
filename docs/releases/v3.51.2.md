Release v3.51.2: a normal restart restores the saved PD7DAY run instead of downloading one during setup, and the day 2-7 tariff sensors reuse the prices their full forecast partners computed (#365). No published value changes.

## Fixed

**A restart blocked setup on a NEMWEB download.** Each region saves the PD7DAY run it fetched to `.storage`, so a restart can publish it at once and fetch in the background. The saved run was used only if it had been fetched within 35 minutes. But PD7DAY is fetched only when AEMO publishes a run, at 07:30, 13:00 and 18:00, so the saved run is usually hours old at a restart. Almost every restart therefore threw it away and waited for a download inside setup. On HA-OCPP (v3.50.0):
- the blocking first refresh took 9.5 s per entry;
- Home Assistant twice logged "Waiting for integrations to complete setup" past 60 s.

Now:
- A saved run fetched within the last 16 hours is restored. The longest gap between publishes is 13.5 hours, from 18:00 to 07:30, and 2.5 hours more covers a fetch that retries and a restart around a publish.
- The restored run is the one NEMWEB serves until the next publish. The background fetch 30 to 50 s later still runs, and replaces it if a newer run is out.
- A saved run older than 16 hours, after a longer outage, still waits for a fresh download, as before.

**The restored run's age is shown.** `last_success_at` and `data_age_hours` used to read None until the background fetch landed, which was fine for a run at most 35 minutes old. They now give the time and age of the fetch that saved the restored run. `is_stale` was already right: it reads true when a publish has superseded the restored run, with `stale_reason` `missed HH:MM run`, until the background fetch replaces it.

## Faster

**The day 2-7 tariffs reuse their full partners' prices.** After #374 and #375 the remaining cost of a tariff sensor's first write was pricing every interval through aemo_to_tariff from an empty cache: 0.07 to 0.19 s of CPU per sensor on HA-OCPP. The day 2-7 import and export sensors priced the same intervals as the full import and export sensors of the same tariff.

Now one price cache serves every sensor of a region that prices the same tariff the same way. It is keyed on the import or export pricing, the distributor, the code priced and the loss factors, and lives on the region's coordinator, so a reload starts it afresh. The values are the same: the golden snapshots do not change. A day 2-7 sensor whose full partner is disabled prices its own intervals, as before.

Measured on a full 336-interval run in the golden harness (`qld_days27_mode`, Energex 6900, the active tariff's four sensors, CPU of the first attribute build, median of 7):

| Sensor | v3.51.1 | v3.51.2 |
|---|---|---|
| Import, full | 8.3 ms | 7.2 ms |
| Export, full | 3.9 ms | 3.7 ms |
| Import, day 2-7 | 7.8 ms | 1.3 ms |
| Export, day 2-7 | 3.9 ms | 1.1 ms |
| **Total** | **23.9 ms** | **13.3 ms** |

The full sensors' change is noise. The pricing step alone of the day 2-7 import sensor falls from 7.1 ms to 0.8 ms, and of the export from 3.2 ms to 0.7 ms: what is left is the cache lookups. On HA-OCPP, where each sensor's pricing took 0.07 to 0.19 s, the two day 2-7 sensors of each region keep only that remainder.
