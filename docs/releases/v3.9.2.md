Release v3.9.2. Three fixes from a re-review of the codebase at v3.9.1, none of which moves a published price.

## A scheduled fetch slot could die silently

`DailyFetchScheduler._on_fire` popped the slot from its pending timers, ran the fetch action, and only then re-armed the next timer, with nothing between the call and the re-arm. `entry.async_create_background_task` raises mid-teardown or mid-reload, and when it did the slot lost its timer permanently, with no log line, until the config entry reloaded — the same failure shape #126 fixed on the coordinator side. The action now runs inside `try`/`except`/`finally`, so the slot always re-arms and a failure is logged instead of disappearing (#140, PR #142).

## Undated observation rows sorted as the newest day

Every ordering operation in `ObservationLog` was a plain string sort, and the sentinel key for a row with no usable `interval_time`, `"undated"`, sorts after every real `"YYYY-MM-DD"` key. That made it read as the newest possible day everywhere: `prune()` reached it last and the never-drop-the-newest-day guard protected it as if it were current, so undated rows accumulated without bound and evicted genuine dated observations from the training window; the flat observation list placed them at the tail as though most recent; and once one existed, every later append compared against that tail and lost, forcing a full rebuild of a list that can hold up to `MAX_TOTAL_OBS` entries on every subsequent append. A shared sort key now orders the undated segment first, since it is not newer than anything (#141, PR #143).

## A stage-2 feature disagreed with the published price at the market floor

The isotonic branch of `BucketModel.apply_all` published the unfloored isotonic prediction as `ISO_FEATURE_KEY` while `calibrated` published the value floored at `MARKET_PRICE_FLOOR`. Every other branch publishes the feature equal to the point estimate, which is the invariant `stage2_iso_feature`'s docstring states the split key exists to protect; fixed to publish the floored value (PR #145).

## Housekeeping

`PD7DayCoordinator._run_features_cache`, added with the per-run cache in v3.9.1, was read via `getattr` and assigned on a miss but never declared in `__init__` alongside its sibling `_calibrated_forecast_cache`; now declared (PR #145). A fourth finding from the same review, that a delayed segment save could recreate a file after `prune()` removed it, was checked against Home Assistant's real `Store` implementation and found not to be a bug: `Store.async_remove()` cancels a pending delayed save on that instance, and `ObservationLog`'s per-date store cache guarantees a prune always removes through the same instance a save was scheduled on. A regression test now pins that instance-reuse invariant.

## What to expect on deploy

No sensors added or removed, no entity ids changed, no attributes, no tariff definitions and no requirements changed. Published prices do not move.

## Patch rather than minor

Three correctness fixes and one declaration cleanup, no behaviour change to what is published.
