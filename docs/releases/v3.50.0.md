Release v3.50.0: triage of the open issues. No price changes. One startup behaviour change, set out under Changed.

## Changed

**A tariff's first write at startup (#365).** Home Assistant writes each entity's state straight after adding it. The region's forecast sensors are added first and warm the calibrated forecast before their own first write. But a startup refit, or an STPASA refetch forced by a stale cache, can move that forecast's key before the tariffs are reached. Each tariff's first write then calibrated the run and priced every interval on the event loop: 0.5 to 1.25 s per sensor on HA-OCPP.

Now, when that happens, a tariff's first write carries its state and every attribute except `forecast`, which is empty. The full write follows as soon as the forecast sensors re-warm, which a refit triggers, through the same wait later writes already use. A region whose forecast sensors are all disabled keeps the old first write, since nothing would re-warm it.

## Fixed

**aemo-to-tariff 0.7.29 (#369).**
- The daily probe against the newest library release failed on 0.7.29 only because pytest started 0.17 s after pip finished. `/proc/stat` gives the boot time in whole seconds, so the process start can read up to a second early, and the library looked as if it had been installed after the process started (the #207 guard). An install within that second is no longer counted as after the start.
- The pin moves to 0.7.29. Its one change, an optional `import_tariff` for Energex 96200 sites, is already covered by pricing that export as 96200X, so no price changes. Each tariff sensor's `library_version` attribute now reads `0.7.29`.

## Diagnostics

**A slow attribute build says why (#363).** When the attribute build of a spot forecast, price timeline or tariff sensor takes 0.2 s or more, it logs at debug:
- the time of each step (calibrated memo, `region_timeline`, `timeline_forecast`, then the summary or the tariff pricing);
- the wall time;
- the loop thread's CPU time over the same span.

A wall time far above the CPU time means the event loop was starved rather than slow. Turn on debug logging for `custom_components.nem_pd7day` to see it.

## Faster

**`cheapest_2h_window` (#363):** computed on epoch seconds rather than datetimes, 4.4 ms to 1.4 ms on a real-size forecast. The values are identical: 8,400 comparisons against the old code agree, and golden snapshots change only in `library_version`.

## Removed

**The bias chart camera and `bias_chart.py` (#367).** No platform ever set the camera up, so no install has the entity. Nothing to remove on upgrade.

## Development

The coverage gate (`scripts/cov_compare.py`) maps lines through git's diff and follows moved blocks, so a moved line is compared with its moved copy rather than an identical line elsewhere (#368).

## Upgrade notes

Home Assistant installs aemo-to-tariff 0.7.29 on the first start after the update. If another integration has already imported the library by then, the log asks for one more restart (#207).

## Minor-level in effect

One behaviour change: the empty `forecast` on a tariff's first write when the calibrated forecast is stale. The suite goes from 2115 to 2132 tests.
