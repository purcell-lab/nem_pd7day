Release v3.8.3. The usual two files, `manifest.json` and the `README.md` version history row.

One PR since v3.8.2: #129, closing #126, #127, #128 and #105. Suite goes from 1017 to 1026 tests.

## Scheduled PD7DAY fetches run again

Since v3.6.0 no scheduled fetch had run. The `DailyFetchScheduler` introduced in #111 handed Home Assistant a plain function as its timer action; HA classifies that as an executor job and runs it on a worker thread, and the fetch task created from that thread was destroyed while pending. The closure it replaced had been decorated `@callback`. Every run served since v3.6.0 arrived through a deploy restart or a manual `homeassistant.update_entity`, which is why nobody noticed until the 5 Sep health check found the 07:30 run missing and five "Task was destroyed but it is pending" errors in the log. The action is now registered as a callback-typed `HassJob`, pinned by a test that fails on the old code.

## Staleness that does not need a failure

`is_stale` only ever flipped on a failed fetch, so a fetch that never ran left it reading false, and `data_age_hours` was a snapshot taken at the last state write, so it read 0.0 for as long as nothing wrote. Now `last_success_at` (a NEM-time timestamp) is published alongside the age; `is_stale` also fires when a publish slot (07:30, 13:00, 18:00 NEM) is 30 minutes past and the run being served predates it, with `stale_reason` `missed 07:30 run`; and the `*_pd7day_data` diagnostic sensor rewrites state on the half hour so its attributes move during an outage. New constant `STALE_RUN_GRACE_MIN` (30).

## The observation window is 90 days again

`MAX_TOTAL_OBS` goes from 20,000 to 100,000. A region logs about 1,070 observations a day, so the old cap held 19 days and the documented 90 day window never bound; the fit, the domain floors and the leverage screen all saw three weeks. The calibration sensor now reports `oldest_observation` and `effective_window_days`, the window the fit could actually see. Observation saves go through Home Assistant's delayed save (300 s) so a burst of settling intervals becomes one file rewrite. The store will grow to about 50 MB per region over the next ten weeks; the whole-file write pattern is tracked in #130.

## What to expect on deploy

Forecasts refresh at 07:30, 13:00 and 18:00 NEM without a restart. `is_stale` may read true briefly on installs whose last served run is older than the latest slot; it clears on the next fetch. The observation store grows daily until it reaches 93 days of history. No sensors added or removed, no entity ids changed, no tariff definitions and no requirements changed. New attributes: `last_success_at` on the forecast and tariff sensors, `oldest_observation` and `effective_window_days` on the calibration sensor.

## Patch rather than minor

Three fixes to behaviour introduced in v3.6.0 and earlier. Published prices do not move.
