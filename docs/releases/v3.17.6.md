Release v3.17.6. The calibration store is split into smaller parts inside; nothing published or stored changes.

## Calibration store split

`CalibrationStore` did six jobs in one 700-line class: persisting the coefficient and forecast-history files, ingesting each forecast run, recording actual prices against the forecasts that covered them, orchestrating the refit, serving calibrated prices, and reporting diagnostics. Five of them now live in modules with no Home Assistant imports (spec 004, PR #197):

- `json_repository`: the coefficient and forecast-history files, with the legacy-key migration that used to be written twice.
- `forecast_history`: joining each PD7DAY run with STPASA, gas and interconnector data, skipping runs already seen, and pruning by age.
- `actual_recorder`: matching actual prices to forecasts, the running average of five-minute readings, and building observations (#43, #132, #147).
- `refit_service`: the fit's inputs, the STPASA feature map and the compression-ratio history record.
- `calibration_summary`: the oldest observation, effective window (#127) and summary attributes.

`CalibrationStore` stays as the object every caller uses and keeps its state, clock and the order of the refit's steps. Serving calibrated prices stays with it until the serving gates are split (spec 005).

## Stored files

A test recorded on the previous code drives the real store through a migration, forecast runs, actual readings, pruning, refits with stage 2 working and failing, a restart and a corrupt coefficient file, and pins every file written, byte for byte, with every fit generation and log line. It passes unchanged on this release, so the files in `.storage` are written exactly as before and a downgrade reads them as before.

## What to expect on deploy

- Every entity, attribute and stored file is as before.
- The calibration sensor's observation count and fit time carry through the restart unchanged.
