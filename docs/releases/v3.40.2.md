Release v3.40.2: STPASA is fetched as soon as a region has none, and setup no longer refreshes every coordinator while it adds the entities. Both were found on a fresh test install of v3.40.1.

## STPASA on a fresh install (#346)

- **Before:**
  - a fresh install, or a restart after more than 4 hours down, forced no STPASA fetch, so the STPASA Data sensor read `unavailable` until the next PD7DAY slot (07:30, 13:00 or 18:00), up to 5.5 hours away;
  - after a long outage the startup refit ran without STPASA.
- **Now:**
  - a region with no usable cache forces the immediate fetch a stale cache already got;
  - an entry added later in the same run is served from that download, with no request of its own;
  - the STPASA Data sensor writes as soon as a fetch is saved, rather than at the next PD7DAY update.

## Setup without a coordinator refresh (#347)

- **Before:** the sensor and binary sensor platforms added their entities with `update_before_add=True`. For a coordinator entity that awaits a coordinator refresh inside platform setup. On a cached restart, setup downloaded and parsed PD7DAY on the spot, and asked dispatch, constraints, P5MIN and pre-dispatch for an extra fetch each. The two-phase startup is built to avoid exactly this. It showed in the log as `Setup of binary_sensor platform nem_pd7day is taking over 10 seconds`.
- **Now:** the entities are added as they are. Every coordinator already gets its data in place, or starts its own first fetch, before the platforms are set up.
