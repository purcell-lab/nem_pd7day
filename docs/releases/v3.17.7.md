Release v3.17.7. The calibration serving path is restructured inside; no published price, band or label changes.

## Serving gates

Every calibrated price the integration publishes passes through `CalibrationResult.apply`, which decides for each interval whether the stage 2 STPASA correction may replace the stage 1 isotonic value. That decision had grown into one 169-line method, each check added for a different defect. It is now an ordered pipeline of six gates in `serving.py` (spec 005, PR #199):

| Gate | Refuses stage 2 when | Issues |
|---|---|---|
| `below_domain` | the forecast is below the stage 1 fit's domain | #73, #114, #117 |
| `stage2_inputs` | the horizon is outside the stage 2 band, or STPASA or run features are missing | |
| `stage2_model` | the bucket has no stage 2 model | |
| `feature_domain` | stage 2 would extrapolate beyond the uncertainty the bucket publishes | #85, #147, #153 |
| `sign_agreement` | stage 2 disagrees with stage 1 on sign | #73, #114 |
| `market_floor` | the prediction is below the market floor | #114 |

The first gate that refuses serves the stage 1 result unchanged; when every gate admits, one builder produces the stage 2 band (#69, #72). The three stage 1 paths (passthrough, below the domain #123, isotonic #114 #144) and the spike credibility annotation (#176) sit beside them. A new gate is now a class and one entry in a list, not an edit to a long method.

## How it was checked

Before any code moved, 35,880 inputs were run through the previous code and every output recorded exactly, reaching every stage 1 path, every gate refusal and both stage 2 bands at least 350 times. The same test passes on this release. The serving path is also about 6 per cent faster.

`SPIKE_THRESHOLD` now lives in `serving.py`; its value is unchanged.
